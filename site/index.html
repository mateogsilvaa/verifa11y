Accessibility fixes that prove themselves.

verifa11y finds the WCAG violations in your HTML, writes the smallest fix for each one and re-checks the page in a real browser. It drops any fix that only silences the checker, and tells you why.

Try it in Claude Code Cursor Codex Windsurf Gemini CLI OpenClaw Zed opencode your terminal GitHub Actions How it works

Open source (Apache-2.0). Runs on your machine. No account, no telemetry.

A checker can go quiet while the page stays broken.

Coding agents write accessibility fixes in bulk and confirm them by re-running a checker. Hide the element, add a generic label or copy the file name into the alt text, and that checker reports nothing. verifa11y keeps a fix only after it passes checks that a hidden or faked fix fails.

A patch has to pass six checks

Each check catches one way to make a violation disappear without fixing it. verifa11y runs all six on every patch, its own codemods included.

role="navigation"verified
alt="plot map"rejected at gate 3
  1. 1

    Gone

    axe-core no longer reports the violation on that element.

    image-alt 1 → 0
  2. 2

    Nothing new

    Every WCAG 2.x A and AA rule, on the whole page.

    new violations: 0
  3. 3

    Nothing faked

    No hidden elements, no “image”, no text that restates a file or field name.

    alt = plot-map.png
  4. 4

    Accessibility tree

    Chromium's computed role, name and state, before and after.

    nav → navigation
  5. 5

    Focus order

    Real Tab presses. Nothing leaves the order or moves.

    7 stops → 7 stops
  6. 6

    Pixels and references

    Nothing outside the patch changes; every reference exists.

    0.00% outside

What the checks can't judge. Whether alt text says what an image is for, whether a state is true, whether a colour fits your design. Most of WCAG needs a person, so read every patch before you apply it.

How to read the naive rows

The naive fixer gets more patches past the verifier than the codemods do, and a reviewer would turn many of them down: invented state, inline colour overrides, a deleted live region. The verifier proves that none of them makes the page worse. Read “verified” as an upper bound on quality.

Before you try it.

Does verifa11y make my site accessible?

No. It fixes specific, machine-detectable violations and proves those fixes didn't make anything worse. Most of WCAG can only be judged by a person. Use it as a first pass you still review.

Does my code leave my machine?

Only if you configure a model or agent for the fixes that need judgment; then the page goes to whatever you configured. No telemetry, no account, no server. Pages render offline.

Do I need an AI model?

No. Codemods fix what can be proven from the markup (misspelled roles, invalid ARIA values, heading levels, simple labels) and the rest is reported as skipped. With a model it also attempts alt text, contrast and widget state.

Which rules does it patch?

image-alt, label, heading-order, aria-allowed-attr, aria-required-attr, aria-valid-attr-value, aria-roles and color-contrast. The verifier checks every WCAG 2.x A/AA rule axe-core has.

What about React, Vue or a live site?

Patching works on static HTML today; frameworks are on the roadmap. verifa11y site audits a live site but only reports: a live page has no source file to patch.

How is “verified” different from “passes axe”?

Passing axe means the rule stopped reporting. Verified also means nothing new broke, nothing was hidden, no name became meaningless, and the accessibility tree, focus order and pixels still agree. On the benchmark, 238 patches pass axe and fail the rest.

Is it free?

Yes. It is Apache-2.0 and lives on GitHub, where you can report bugs and send changes.

Claude Code

  1. Install the browser verifa11y renders with, once.

    npx verifa11y-mcp --install-browser

  2. Add the server from your project folder.

    claude mcp add verifa11y -- npx -y verifa11y-mcp --root .

  3. Ask your agent in plain words, for example: “Fix the accessibility of index.html with verifa11y.” It gets a patch to review, never an edited file.

Ollama (local)

  1. Install the browser, once.

    npx verifa11y install-browser

  2. Audit the page.

    npx verifa11y audit page.html --out findings.json

  3. Let a local model write the fixes that need judgment. Fully offline; every patch still faces the six checks.

    npx verifa11y fix findings.json --verify --strict --generator-cmd "ollama run qwen3:8b --think=false"

  4. Review and apply.

    git apply patches/verifa11y.patch

Terminal

  1. Install the browser, once.

    npx verifa11y install-browser

  2. Audit a page: every violation, with its rule, WCAG criterion and source lines.

    npx verifa11y audit page.html --out findings.json

  3. Fix and verify. Only patches that pass all six checks make it into the output.

    npx verifa11y fix findings.json --verify --strict --out patches

  4. Read the report, then apply what you agree with.

    git apply patches/verifa11y.patch

  5. Optional: any agent CLI can write the fixes that need judgment.

    npx verifa11y fix findings.json --verify --strict --generator-cmd "claude -p"

GitHub Actions

  1. Add a workflow. On every pull request it audits the HTML that changed.

    name: accessibility
on:
  pull_request:
    paths: ["**/*.html"]
permissions:
  contents: read
  pull-requests: write
jobs:
  verifa11y:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}
          persist-credentials: false
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - uses: mateogsilvaa/verifa11y@v0.4.1

  2. Verified fixes arrive as suggestions on the exact lines. Suspicious and skipped findings are listed for a person, never suggested.
